## Implemented contracts

The existing `seo-release-gate.mjs` retains its failure-array API and exit code. `inspectSeoRelease` and `--report` expose route records for initial HTML/main H1, meaningful unique metadata, current canonical/indexability/discovery, route-correct Open Graph, supported brief content/media/links, every JSON-LD block, factual business identity, known private-location leakage, remnants and local assets. Similarity excludes shared shell/conversion/business facts; its score is diagnostic. Exact long page-substance duplication after locality/service substitution blocks. Word count remains a smoke check.

The browser verifier uses the same approved route inventory. Every route receives desktop/mobile checks; representative page types also receive compact/tablet checks. It exercises direct HTTP, refresh, contextual navigation, back/forward, keyboard disclosure/focus, reduced motion, overflow, assets, runtime and console errors. Invalid slugs and unknown paths must return real HTTP 404. The existing painted contrast audit retains all routes and interaction states; failed or unresolved paint remains blocking.

Required service/location/contact forms must be present. Native and shared React forms must render, initialize, preserve input on failed/network-failed delivery and reset after exactly one success event. Native success clears submitted contact values and defaults without changing hidden routing tokens or failed input. Requests are intercepted before delivery; no request body is persisted. Unsupported/disabled forms remain unverified and block that scope. Mock success proves the frontend lifecycle, not actual provider acceptance or email delivery.

`verify-site-routes.mjs` combines these results into an evidence handoff without becoming creative-promotion authority. The handoff records checkout commit, dirty state, config digest, brief version, route identity, expectations/observations, screenshots, provenance identifiers, omissions/issues and blocker dependencies. Reports redact configured tokens, URL credentials/queries and known private locations. Keep evidence outside public `dist` and in private CI artifacts.

## Run local verification

Use a reviewed generated client build with its appropriate `PUBLIC_SITE_URL` and `PUBLIC_REVIEW_MODE`. From the control repository, pass the client checkout path explicitly:

```bash
node scripts/verify-site-routes.mjs \
  --config /path/to/client/src/site.config.json \
  --dist /path/to/client/dist \
  --site /path/to/client \
  --mode production --origin https://approved-project.pages.dev \
  --report /private/evidence/route-handoff.json \
  --screenshots /private/evidence/screenshots
```

For a non-indexable review build, use `--mode review`; no production-readiness claim follows from that result. The runner intercepts all mutating browser requests. It does not authorize paid generation, emails or real test submissions.

Run owned fixture regression coverage with `npm run verify:site-route-fixtures`. The authored fixture is the positive full-site baseline. Static care/trades fixtures retain known legacy homepage contrast findings as negative release cases; their technical/browser checks must pass, and any non-homepage contrast regression fails the fixture runner. A diagnostic fixture never counts as a promoted creative candidate or ready client site.

## Workflow and migration

Generation and revision keep their existing acceptance gates and add the approved-route browser report; the technical gate persists its report. The revision synchronizer can migrate the shared layout/about metadata from exact known generated hashes, preserving client edits. Unknown customized layouts require developer review, including new route-specific Open Graph tags and stable business schema ID; do not overwrite them to pass a gate. Existing approved client commits that lack this contract must be migrated and reviewed before future publishing.

A top-level non-indexable 404 page prevents Pages SPA fallback from turning unknown paths into homepage HTTP 200 responses. It is copied through the same exact-hash-safe revision migration. Local host verification emulates Pages fallback when this artifact is absent.

The publish workflow still requires approved commit checkout, existing contrast/SEO gates and full local route scope before upload. Only a clean production checkout with passing local evidence can write `.launchloom-release.json`, containing commit/config digest and hashes of public built files. After upload, GET-only verification reads that manifest and every expected public artifact at its canonical public URL back from the approved Pages origin, omits host-only configuration files from fetchable assets, rejects unexpected redirects, detects stale/mismatched bytes and real-host soft 404s, and runs destination browser interactions with intercepted forms. The byte-matched local contrast audit and destination browser evidence are explicitly distinct. Client notification happens only after both destination scopes pass.

Actual Pages/Worker workflow conclusion and deployment SHA must still be read back during authorized shipping. A served manifest is source/artifact evidence, not independent provider deployment metadata. Custom domains, analytics, legal policy authoring and real-provider testing remain separate scopes.
