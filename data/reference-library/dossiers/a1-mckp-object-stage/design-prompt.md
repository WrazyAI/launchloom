# MCKP interactive object stage: archive-only design implementation brief

This document extracts visual mechanics from the permission-cleared source captures. It is not source copy and does not grant permission to reuse any source brand asset. The dossier is archive-only and is not eligible for automatic production selection.

## visual hierarchy
Build an object-led product stage, not a bento-style SaaS template. Start with a small utility nav and a short, oversized two-line promise above one isolated product render on a nearly black material field. Let the object establish the page's visual hierarchy. Follow it with a scene/gallery rail, a product-use demonstration, a capability atlas, customization proof, integrations, and a concise release log. Use dark negative space, focused light, restrained accent colors, small technical labels, and a neutral sans with a limited serif accent. Every scene must show a real customer task or a verified product capability.

## page sequence
Keep the rhythm: object hero; browseable scenes; embed/use case; a small number of capability demonstrations; customization or process; verified integration list; release/change log; one strong final CTA. Do not replace the concept with uniform cards. If there is no client product imagery, request/generate original asset scenes bound to content tokens.

## responsive translation
On mobile, place the object first, keep type compact enough to avoid clipping, stack feature scenes, and convert hover transitions into tap-safe controls. No horizontal page overflow. Disable pointer drift and heavy rendering on touch or reduced-motion devices, and show a high-quality static object image immediately if 3D fails.

## signature elements
Required mechanics: an isolated central object, material/lighting contrast, a progressive set of product scenes, and a clear non-motion fallback. Use an object that genuinely represents the client's product; do not reuse MCKP's phone, interface screenshots, texture, or model.

## prohibited patterns
Never reproduce MCKP's product scenes, UI, copy, logo, fonts as a requirement, features, price, claims, or exact composition. Do not add unrelated 3D decoration, auto-playing scenes without pause, canvas-only text, fake integrations, or untested GPU effects. The page must remain legible and navigable if all motion and WebGL are disabled.

## local-business translation and SEO
For a LaunchLoom client, translate this composition only after grounding the page in the client's verified business kind, services, service area, customer questions, contact channels, assets, and SEO research. Keep the opening statement useful to the actual searcher, use natural service/location language, answer the real decision questions, and place one primary conversion action early. Never copy source copy, logos, people, photos, products, claims, or interface assets. Any missing fact remains absent or is requested from the client; do not fill it with a plausible invention. Keep semantic headings, keyboard and touch access, sufficient contrast, reduced-motion behavior, and a working form or call action.

### Type, surfaces and image roles

- Display character: neutral modern sans with a restrained instrument-serif accent. Body character: compact technical sans and mono labels. Hierarchy: large two-line display headline, small product microcopy, medium feature headings. Translate these roles to the host's local font catalog and honor client-selected heading/body families. Specify a responsive scale, line-height and intentional wrapping; keep body lines under about 80 characters. Do not copy source font files or fetch remote fonts.
- Source surface cues: black; charcoal; smoke; select white/gray demo surfaces. Contrast intent: dark scenes carry readable white type; bright interface demo panels are limited to clear product evidence. Propose 4-6 named client-compatible color tokens with hex values in the contract, labeled as implementation choices, not measured source colors. Bind them to the host's accessible per-surface palette roles rather than overriding client brand variables.
- Media role: photoreal 3D device/mockup rendering against rough dark materials. Crop guidance: isolated hero object, scene thumbnails, then close-up interface panels. Focal role: the device or interface state being demonstrated. Map opening/secondary/detail placements to the available client image tokens. Preserve role, focal point and mobile crop without using reference screenshots as site assets. If the right media is absent, use an allowed contextual asset or deliberate graphic treatment, and flag any signature that cannot be met; never imply stock people or spaces belong to the client.
- Service presentation: capabilities appear as an ordered technical atlas with an image, interface state, and concise explanation. Early action: directly beneath the hero object. Primary placement: Start for free or the client's genuine main product action. Name the actual client next step; repeat it at decision points, not mechanically after every chapter.

### Mobile and interaction translation

Recorded mobile strategy: **object-first vertical sequence with poster fallbacks**. show the device before small explanatory copy; stack scene previews into a vertical list or swipe-safe gallery; keep product interface labels legible; avoid sticky scaling stacks on narrow devices; disable cursor-only effects and provide touch interactions; preserve a static render if 3D is unavailable.

Record separately what stacks, reorders, changes crop, wraps, becomes a menu or becomes a touch control. Do not just shrink desktop. Keep the primary action, visible focus, labels and form controls usable without hover or motion; no horizontal overflow or competing sticky overlays. Recorded interaction opportunity: slow, cursor-aware object focus and scroll-revealed product scenes. Reduced-motion contract: provide a static device render and immediate scene navigation. Implement only the justified documented interaction, with equivalent static content. Do not add repeated fade-up entrances, autoplay or section pinning to compensate for an unclear layout.

### Plan, build and critique

Before code, use the existing contract stage to state the client's audience and primary task, choose the token system, draw desktop/mobile wireframes, map chapters to content, and name one memorable reference-led element. Check against this family's composition and prohibited patterns; revise any choice that could belong to an unrelated generic page. Source-required cream/serif, dark accents, uppercase navigation, cards or rules are legitimate when they serve this specific reference, not automatic reasons to redesign it.

Build from the revised contract. Then inspect rendered desktop, compact desktop and mobile, including menu/form/disclosure states. Compare actual geometry, section rhythm, image roles and every signature with the paired references, not just DOM markers. Verify contrast, working calls/links/forms, keyboard focus, reduced motion, truthful content and no em dashes in rendered copy. Remove decoration that does not serve the brief. Report any unmet signature or unavailable evidence; do not claim rendered fidelity from a successful build alone.
